**Body:**

Hello Sovereign AI Community,

Since our early release, the Sovereign AI Stack has stood as a reference implementation for offline-first, local RAG with policy gating and audit logging. 

Today, we are taking a massive leap forward. With the **v2.0 Strategic Maturation and Refactor**, we are shifting from an "interesting local prototype" to a **global reference architecture for provable, hardware-anchored sovereignty**.

### 🌟 The Core Pillars of Sovereign AI v2.0

To achieve true zero-trust AI infrastructure, we are refactoring our core components around five critical security and architectural pillars:

1. **Attestation Isolation (SGX/SEV)**: Moving cryptographic verification into secure enclaves to establish isolated process boundaries and remote attestation TLS (RA-TLS).
2. **TPM-Sealed Keys**: Binding database encryption keys to physical Platform Configuration Registers (PCRs) to ensure data-at-rest keys can never be unsealed on tampered platforms.
3. **Async Audit Ledger**: Decoupling audit logging from the request-response path using asynchronous background workers that stream signed Merkle checkpoints to immutable WORM storage.
4. **Ontology-Driven Policy Engine (OWL/RDF)**: Upgrading our simple policy gates to support role inheritance, wildcard expansion, and logical overlap resolution using formal ontologies.
5. **Adversarial NLI Calibration**: Protecting the semantic airlock from jailbreaks and linguistic evasion by retraining our NLI evaluator on adversarial datasets and implementing an ensemble scorer.

*   **NIST Zero Trust (SP 800-207)**: Strict policy gating at the agent retrieval layer prior to model execution.

<a name="pillar-1-attestation-isolation"></a>
### 1. Attestation Isolation
*   **Title:** Refactor AttestationVerifier into Enclave Microservice
*   **Labels:** `security`, `architecture`, `help wanted`
*   **Description:**
    ```markdown
    ### Problem Statement
    Currently, attestation checking and secure anchors are evaluated within the main application process. For true process isolation, the attestation verification logic must be isolated within a secure enclave (Intel SGX, AMD SEV, or AWS Nitro Enclave).

    ### Proposed Architecture
    1. Extract attestation verification out of the agent code.
    2. Build a standalone attestation microservice container that establishes a mutual TLS (mTLS) connection with the main agent using Remote Attestation (RA-TLS).
    3. The agent will query this service via gRPC to verify hardware-signed nonces and quotes.

    ### Relevant Files
    * `sovereign_ai/common/hardware_trust/mock_sim.py`
    * `sovereign_ai/common/hardware_trust/base.py`

    ### Deliverables & Acceptance Criteria
    - [ ] Standalone Dockerized verification service containing the enclave validation logic.
    - [ ] gRPC interface for the agent to request quote validations.
    - [ ] Verification client integration inside `sovereign_ai/common/hardware_trust/`.
    - [ ] Unit tests covering RA-TLS quote validation, network channel failures, and fail-closed behaviors.
    ```

<a name="pillar-2-tpm-sealed-keys"></a>
### 2. TPM-Sealed Keys
*   **Title:** Implement TPM-Sealed SQLCipher Key Management
*   **Labels:** `security`, `crypto`, `help wanted`
*   **Description:**
    ```markdown
    ### Problem Statement
    Our current database encryption relies on SQLCipher passwords supplied via environment variables or keyring. We need to transition to hardware-sealed keys where keys are sealed into TPM 2.0 NVRAM.

    ### Proposed Architecture
    1. Seal the SQLCipher database encryption keys in the platform TPM NVRAM.
    2. Enforce PCR-gated unsealing (Platform Configuration Registers 0-7 or application measurement PCR 11), ensuring keys can only be unsealed if the host platform boots in a trusted, unmodified state.
    3. Implement key derivation using PBKDF2 with a hardware-anchored salt to prevent key extraction from memory.

    ### Relevant Files
    * `sovereign_ai/agent/tpm_signer.py`
    * `sovereign_ai/rag/store.py`
    * `sovereign_ai/rag/db_utils.py`

    ### Deliverables & Acceptance Criteria
    - [ ] Key sealing and unsealing interface leveraging `tpm2-pytss` or native OS TPM wrappers.
    - [ ] Integration with `sovereign_ai/rag/store.py` to transparently unseal and apply keys to SQLCipher on database start.
    - [ ] PCR state validation helper validating current system state against a signed PCR gold manifest.
    - [ ] Automated tests using a mock TPM simulator when physical TPMs are not available.
    ```

<a name="pillar-3-async-audit-ledger"></a>
### 3. Async Audit Ledger
*   **Title:** Build Asynchronous Append-Only Audit Ledger
*   **Labels:** `security`, `logging`, `help wanted`
*   **Description:**
    ```markdown
    ### Problem Statement
    Merkle tree recomputations and signing operations are executed synchronously during user requests, creating latency bottlenecks. We need a performant, asynchronous logging path.

    ### Proposed Architecture
    1. Implement an async task queue (e.g., using `asyncio` or a lightweight background thread worker) to ingest audit logs out-of-band.
    2. Accumulate logs in blocks, sign the block Merkle root using the hardware TPM key, and write checkpoints to an append-only WORM (Write Once Read Many) storage endpoint.
    3. Support multiple pluggable WORM targets (e.g., local TPM NVRAM index, AWS S3 Object Lock, IPFS, or a decentralized hyperledger).

    ### Relevant Files
    * `sovereign_ai/agent/forensics/`
    * `tests/certification/generate_report.py`

    ### Deliverables & Acceptance Criteria
    - [ ] Background worker daemon using `asyncio.Queue` or background threads for ledger logging.
    - [ ] WORM storage interface with concrete implementations for S3 Object Lock and local TPM NVRAM.
    - [ ] Performance benchmarks showing synchronous vs. asynchronous write latency differences.
    - [ ] Verification script to check ledger consistency and tamper-detection under concurrent request loads.
    ```

<a name="pillar-4-ontology-policy-engine"></a>
### 4. Ontology Policy Engine
*   **Title:** Upgrade Policy Verifier to Ontology-Driven Model
*   **Labels:** `security`, `policy`, `help wanted`
*   **Description:**
    ```markdown
    ### Problem Statement
    The current ABAC policy engine uses prefix/attribute-matching which becomes complex to scale and lacks nested hierarchy or role-inheritance. We want to represent and verify policies using formal OWL/RDF models.

    ### Proposed Architecture
    1. Upgrade policy models to use formal RDF/OWL formats.
    2. Support hierarchical inheritance (e.g., a "lead-doctor" inherits all permissions of "doctor").
    3. Use SPARQL queries or Z3 logical formulations to evaluate wildcards and automatically identify overlapping or contradictory rules.

    ### Relevant Files
    * `sovereign_ai/verify/policy_z3.py`
    * `docs/GOVERNANCE_MODEL.md`

    ### Deliverables & Acceptance Criteria
    - [ ] RDF/OWL representation for ABAC policies.
    - [ ] SPARQL-based query resolver or expanded Z3 solver capability that resolves hierarchical rule overrides.
    - [ ] Diagnostic test suite to verify conflict detection, transitive role inheritance, and wildcards.
    ```

<a name="pillar-5-adversarial-nli-gate"></a>
### 5. Adversarial NLI Gate
*   **Title:** Retrain NLI Gate with Adversarial Datasets
*   **Labels:** `ml`, `security`, `help wanted`
*   **Description:**
    ```markdown
    ### Problem Statement
    The current DeBERTa-based Natural Language Inference (NLI) gate is vulnerable to linguistic evasion and advanced jailbreaks where the model can be fooled by clever phrasing or negation.

    ### Proposed Architecture
    1. Retrain or fine-tune our NLI model (DeBERTa-v3-base) using adversarial datasets (like SNLI-Hard, ANLI, and custom evasion inputs).
    2. Build an ensemble scoring architecture that combines predictions from the NLI cross-encoder model with a rule-based contradiction detector.
    3. Ensure latency is kept under 60ms on CPU to prevent user bottlenecks.

    ### Relevant Files
    * `sovereign_ai/verify/nli_calibration.py`
    * `sovereign_ai/verify/evaluator.py`
    * `sovereign_ai/verify/ensemble.py`

    ### Deliverables & Acceptance Criteria
    - [ ] Fine-tuning/distillation script using ANLI/SNLI-Hard.
    - [ ] Ensemble decision module (`sovereign_ai/verify/ensemble.py`) containing the joint classifier scoring.
    - [ ] Automated robustness evaluation benchmark demonstrating resistance to negation and jailbreaks.
    ```
